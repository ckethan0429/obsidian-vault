# 5편 근거 — 디자이너 바이브코딩 입문

> 연재 계획: [[threads-series-terminal-agents-for-everyone]]
> 대상: 코딩을 모르는 디자이너. 목표: "말로 설명하면 실제로 작동하는 화면이 나온다"를 직접 체험하게 한다.
> 이 문서는 편 작성용 상세 근거 자료입니다. Threads 게시본이 아니라, 그 근거가 되는 사실·예시 모음입니다.

## 0. 바이브코딩이 뭔가요

**바이브코딩(vibe coding)** 은 코드를 한 줄도 직접 쓰지 않고, 원하는 것을 평범한 말로 설명하면 AI가 알아서 코드를 만들어 주는 방식입니다. 2025년 초에 널리 퍼진 표현으로, 뜻은 간단합니다. "만들고 싶은 걸 말로 부탁하고, 나온 결과를 보면서 다시 고쳐 달라고 부탁하는 것"입니다.

- 예전: 웹페이지를 만들려면 HTML·CSS 같은 코드 문법을 배워야 했습니다.
- 지금: "위쪽에 큰 제목, 그 아래 파란 버튼 하나 놓아 줘"라고 말하면 화면이 나옵니다.

여기서 **터미널 에이전트(Claude Code, Codex)** 가 왜 특별한지가 중요합니다. ChatGPT 앱에 물어보면 "코드를 화면에 보여만" 줍니다. 그 코드를 어디에 붙여 넣어야 작동하는지는 알려 주지 않습니다. 반면 터미널 에이전트는 **내 컴퓨터 안에 실제 파일을 직접 만들고, 고치고, 저장까지** 해 줍니다. 부탁이 끝나면 폴더 안에 진짜로 열리는 `index.html` 같은 파일이 생겨 있습니다. 이게 "답을 주는 도구"와 "결과물을 만드는 도구"의 차이입니다.

### 준비물
- 컴퓨터에 Claude Code 또는 Codex가 설치되어 있어야 합니다(연재 1편 내용).
- 작업할 빈 폴더 하나. 예: `바탕화면/내첫웹페이지`
- 그게 전부입니다. 코드 편집기도, 문법 지식도 필요 없습니다.

## 시나리오 A — 말로 설명한 걸 작동하는 웹페이지로

가장 먼저 체험하기 좋은 작업입니다. 머릿속 그림을 그대로 말하면 됩니다.

**실제 지시문 예시:**
```
이 폴더에 카페 소개 웹페이지를 하나 만들어 줘.
- 맨 위에 "모닝 로스터리"라는 큰 가게 이름
- 그 아래 한 줄 소개: "매일 아침 직접 볶는 원두"
- 가운데에 원두 사진이 들어갈 자리 하나
- 맨 아래에 영업시간(평일 8시-20시)과 전화번호(02-000-0000)
- 전체 분위기는 따뜻한 갈색 톤, 글씨는 깔끔하게
파일 이름은 index.html로 하고, 다 만들면 브라우저에서 어떻게 열어보는지도 알려 줘.
```

**결과 형태:**
- 폴더 안에 `index.html` 파일이 생깁니다.
- 그 파일을 더블클릭하면 브라우저(크롬 등)에서 실제 페이지가 열립니다.
- 갈색 톤, 제목, 소개 문구, 사진 자리, 영업시간이 배치된 진짜 화면이 보입니다.

**이어서 고치기(바이브코딩의 핵심):** 마음에 안 들면 다시 말로 부탁합니다.
```
버튼 색이 너무 진해. 조금 연한 갈색으로 바꾸고,
가게 이름 글씨를 더 크게 키워 줘.
```
에이전트가 같은 파일을 고쳐 저장합니다. 브라우저를 새로 고치면 바뀐 화면이 나옵니다. 이 "부탁 → 확인 → 다시 부탁"의 반복이 바이브코딩입니다.

**주의점:**
- 사진 자리는 "자리"만 만들어집니다. 실제 원두 사진 파일은 내가 폴더에 넣고 "방금 넣은 beans.jpg를 그 자리에 넣어 줘"라고 말해야 합니다.
- 이렇게 만든 페이지는 내 컴퓨터에서만 열립니다. 남에게 보여주려면 인터넷에 올리는 과정이 따로 필요합니다(6편 GitHub Pages 참고).

## 시나리오 B — 시안 이미지를 화면으로

손으로 그린 스케치나 피그마 캡처 이미지를 화면으로 옮기는 작업입니다.

**실제 지시문 예시:**
```
방금 이 폴더에 넣은 시안 이미지(mockup.png)를 봐 줘.
이 레이아웃대로 작동하는 웹페이지를 만들어 줘.
색깔과 배치는 시안과 최대한 비슷하게,
글자 내용은 시안에 적힌 그대로 써 줘.
```

**결과 형태:**
- 에이전트가 이미지를 읽고, 위에서 아래로 어떤 요소가 있는지 파악해 비슷한 화면을 만듭니다.
- 완벽한 복제가 아니라 "80% 닮은 출발점"이 나온다고 생각하면 됩니다.

**주의점:**
- 이미지→화면 변환은 도구·모델에 따라 정확도 차이가 큽니다. 간단한 레이아웃(제목+글+버튼)은 잘 되지만, 복잡한 그래픽·미세한 간격은 어긋납니다.
- 나온 결과를 보고 "왼쪽 여백을 더 넓게", "이 두 칸을 나란히"처럼 말로 다듬는 과정을 반드시 거쳐야 합니다. 한 번에 완성되길 기대하지 마세요.

## 시나리오 C — 색·폰트 규칙을 코드로 정리 (디자인 토큰)

디자이너에게 특히 유용합니다. **디자인 토큰**은 어려운 말 같지만, 뜻은 "우리 브랜드가 쓰는 색·글씨 크기·여백 값을 한곳에 이름 붙여 정리한 목록"입니다. 예를 들어 "메인 색 = #2B6CB0", "제목 크기 = 32px"처럼요. 이렇게 정리해 두면 나중에 색 하나를 바꿀 때 목록 한 줄만 고치면 전체가 따라 바뀝니다.

**실제 지시문 예시:**
```
우리 브랜드 색과 글씨 규칙을 코드 파일로 정리해 줘.
- 메인 색: 진한 파랑 #2B6CB0
- 보조 색: 밝은 회색 #F7FAFC
- 강조 색: 주황 #DD6B20
- 제목 글씨 크기: 큰 것 32px, 중간 24px, 본문 16px
- 기본 여백 단위: 8px
이 값들을 이름 붙여서 tokens.css 파일로 만들고,
각 값이 뭘 뜻하는지 주석으로 설명도 달아 줘.
```

**결과 형태:**
- `tokens.css` 파일이 생기고, 안에 `--color-main: #2B6CB0;`처럼 이름이 붙은 값 목록이 정리됩니다.
- 앞으로 만드는 페이지에서 "메인 색은 아까 정한 토큰 값을 써 줘"라고 하면 일관되게 적용됩니다.

**주의점:**
- 토큰을 정해 두면 브랜드 통일성이 확 올라갑니다. 하지만 이 파일 자체는 개발자와 협업할 때 진가를 발휘합니다. 혼자 페이지 한 장 만들 때는 없어도 됩니다.

## 시나리오 D — 반복되는 컴포넌트 자동 생성 (버튼·카드)

같은 모양의 버튼이나 카드를 여러 개 만들 때, 하나만 잘 만들면 나머지는 복제·변형을 시킬 수 있습니다.

**실제 지시문 예시:**
```
상품 카드를 하나 예쁘게 만들어 줘.
카드에는 상품 사진 자리, 상품 이름, 가격, "담기" 버튼이 들어가.
그리고 이 카드 모양 그대로, 아래 3개 상품으로 3장을 나란히 만들어 줘.
1) 아메리카노 4500원
2) 카페라떼 5000원
3) 콜드브루 5500원
```

**결과 형태:**
- 똑같은 디자인의 카드 3장이 나란히 배치된 화면이 나옵니다.
- 나중에 "카드 모서리를 더 둥글게"라고 하면 3장 전부 한 번에 바뀝니다.

**주의점:**
- "담기 버튼"은 눌리는 모양은 나오지만, 실제로 장바구니에 담기는 기능(뒤에서 데이터를 처리하는 일)은 없습니다. 겉모습(화면)까지가 바이브코딩으로 쉽게 되는 영역이고, "진짜 작동하는 쇼핑 기능"은 개발이 필요합니다.

## 시나리오 E — 간단한 랜딩페이지 한 장 완성

위 조각들을 합치면 실제로 쓸 수 있는 한 장짜리 소개 페이지(랜딩페이지)가 나옵니다.

**실제 지시문 예시:**
```
내 포트폴리오 소개용 한 장짜리 랜딩페이지를 만들어 줘.
- 맨 위: 내 이름 "김디자인"과 직함 "브랜드 디자이너"
- 그 아래: 나를 소개하는 두세 문장 (내용은 "안녕하세요..."로 네가 자연스럽게 채워 줘, 나중에 내가 고칠게)
- 대표 작업 3개를 카드로 (제목만, 사진 자리 포함)
- 맨 아래: 이메일 연락처와 인스타 링크 자리
- 휴대폰으로 봐도 깨지지 않게 만들어 줘
```

**결과 형태:**
- 스크롤 되는 한 장짜리 소개 페이지 `index.html`이 완성됩니다.
- "휴대폰으로 봐도 깨지지 않게"라고 하면 화면 크기에 맞춰 배치가 조정됩니다(반응형).

**주의점:**
- 실제 내용(소개 문구, 작업 사진)은 내가 채워 넣어야 완성입니다.
- 세상에 공개하려면 인터넷 주소가 필요합니다 → 6편에서 무료로 올리는 법을 다룹니다.

## 어디까지 되고, 어디서 개발자가 필요한가 (솔직하게)

디자이너가 코딩 배경 없이 바이브코딩으로 할 수 있는 것과, 개발자의 손이 필요한 것을 구분하는 것이 이 편의 핵심입니다. 과장하지 않는 것이 신뢰를 만듭니다.

**혼자서 충분히 되는 것:**
- 화면 겉모습 만들기: 소개 페이지, 포트폴리오, 이벤트 안내 한 장
- 색·폰트·여백 규칙 정리, 반복 요소(버튼·카드) 찍어내기
- 시안을 대략적인 출발점 화면으로 옮기기
- 만든 화면을 말로 계속 다듬기

**개발자(또는 더 깊은 학습)가 필요한 것:**
- 실제로 "작동하는" 기능: 회원가입, 로그인, 결제, 장바구니에 담기
- 정보를 저장하고 불러오는 일(데이터베이스): 예약 내역, 주문 기록
- 여러 페이지가 서로 연결되고 데이터를 주고받는 서비스
- 보안, 개인정보 처리, 대량 트래픽 대응

한 줄 요약: **바이브코딩은 "보이는 것"까지는 디자이너 혼자 멀리 갑니다. "뒤에서 돌아가는 것"부터가 개발의 영역입니다.** 이 선을 알면 헛된 기대 없이 도구를 제대로 씁니다.

## 팩트 체크 메모 (2026-08-29 기준)
- 바이브코딩 정의: 자연어로 원하는 것을 설명하면 LLM이 코드를 생성하는 방식. 결과를 보며 후속 프롬프트로 다듬음(위키백과 정의 확인).
- 터미널 에이전트의 차별점(로컬 파일 직접 생성·수정)은 연재 핵심 각도와 일치. Claude Code/Codex는 실제 폴더에 파일을 쓰고 고침 — 검증된 표준 기능.
- "겉모습은 되지만 백엔드 기능은 개발 필요"는 과장 없는 현실적 경계. 이 선을 명시하도록 편을 구성.
