# 6편 근거 — GitHub, 개발 말고도 활용하기

> 연재 계획: [[threads-series-terminal-agents-for-everyone]]
> 근거 개념: [[agent-workflow-developer]]의 버전관리·배포 골격을 비개발자용으로 환원.
> 대상: 코딩을 모르는 일반 직장인·디자이너. 목표: "GitHub은 개발자만 쓰는 곳"이라는 오해를 풀고, 글·자료·홈페이지 관리 도구로 쓰게 한다.
> 이 문서는 편 작성용 상세 근거 자료입니다. Threads 게시본이 아닙니다.

## 0. GitHub이 뭔가요 (개발 빼고 설명하면)

**GitHub**을 개발 이야기를 다 빼고 설명하면 이렇습니다. **"파일을 인터넷에 저장해 두는 창고인데, 언제 누가 무엇을 왜 바꿨는지 전부 기록이 남는 특별한 창고"** 입니다. 구글 드라이브와 비슷해 보이지만 결정적 차이가 있습니다.

- 구글 드라이브: 파일을 덮어쓰면 이전 버전이 사실상 사라집니다(일부만 30일 보관).
- GitHub: 저장할 때마다 "이 시점의 상태"가 통째로 남습니다. 1년 전 3월에 어떤 문구였는지, 누가 왜 바꿨는지 언제든 되돌려 볼 수 있습니다.

여기서도 **터미널 에이전트(Claude Code, Codex)** 의 강점이 나옵니다. 원래 GitHub은 명령어를 외워야 쓸 수 있어서 비개발자에게 벽이 높았습니다. 하지만 이제는 "이 폴더를 GitHub에 백업해 줘"라고 **평범한 말로 부탁하면 에이전트가 필요한 명령을 대신 실행** 해 줍니다. 창고 사용법을 몰라도 창고를 쓸 수 있게 된 것입니다.

### 미리 알아둘 세 단어 (딱 이만큼만)
- **저장소(repository, 줄여서 repo):** GitHub 안에 만드는 폴더 하나. "이 프로젝트 창고"라고 생각하면 됩니다.
- **커밋(commit):** 현재 상태를 하나의 기록으로 저장하는 것. "지금 이 시점을 사진으로 찍어 남긴다"에 가깝습니다. 커밋할 때마다 "무엇을 왜 바꿨는지" 한 줄 메모를 답니다.
- **푸시(push):** 내 컴퓨터의 기록을 인터넷의 GitHub 창고로 올려보내는 것.

이 세 가지는 이름만 알아두면 됩니다. 실제로는 에이전트에게 말로 시키면 됩니다.

### 준비물
- GitHub 무료 계정(github.com에서 가입, 이메일만 있으면 됨).
- 컴퓨터에 Claude Code 또는 Codex 설치.
- 대부분의 팀·개인 용도는 전부 무료 요금제로 됩니다.

## 시나리오 A — 문서·글 버전 관리 (언제 뭘 왜 바꿨는지 기록)

글을 쓰고 고치다 보면 "지난주 버전이 더 나았는데"라는 순간이 옵니다. GitHub은 이걸 완벽히 해결합니다.

**실제 지시문 예시:**
```
이 폴더(제안서_초안)를 GitHub으로 버전 관리하고 싶어.
- GitHub에 "proposal-2026"이라는 비공개 저장소를 새로 만들어 줘.
- 지금 폴더 안 파일들을 첫 기록으로 올려 줘.
- 기록 메모는 "초안 1차 완성"으로 남겨 줘.
계정 연결이 안 돼 있으면 어떻게 로그인하는지 먼저 알려 줘.
```

며칠 뒤 글을 고친 다음:
```
방금 제안서에서 가격 부분이랑 일정표를 수정했어.
지금 상태를 새 기록으로 저장하고 GitHub에 올려 줘.
메모는 "가격 조정, 일정 2주 연장 반영"으로.
```

**결과 형태:**
- GitHub에 저장소가 생기고, 파일들이 올라갑니다.
- 저장할 때마다 "초안 1차 완성", "가격 조정, 일정 2주 연장 반영" 같은 기록이 시간순으로 쌓입니다.
- GitHub 웹사이트에서 각 기록을 눌러 "그때는 무슨 글자였는지"를 볼 수 있고, 원하면 그 시점으로 되돌릴 수 있습니다.

**주의점:**
- 저장소를 만들 때 **비공개(private)** 인지 **공개(public)** 인지 꼭 확인하세요. 제안서·계약서 같은 민감한 문서는 반드시 비공개로 만들어야 합니다. "비공개로 만들어 줘"라고 명시하세요.
- 워드(.docx)나 한글(.hwp) 같은 파일도 올라가긴 하지만, "무엇이 바뀌었는지 글자 단위 비교"는 텍스트 파일(.md, .txt)에서만 깔끔하게 보입니다.

## 시나리오 B — 자료 백업 (컴퓨터가 고장 나도 안전)

중요한 자료를 정기적으로 인터넷 창고에 복사해 두는 용도입니다.

**실제 지시문 예시:**
```
내 "작업자료" 폴더를 GitHub에 백업하고 싶어.
- "work-backup"이라는 비공개 저장소를 만들고 지금 상태를 통째로 올려 줘.
- 용량이 아주 큰 동영상 파일은 빼고 올려 줘(GitHub은 큰 파일에 안 맞아).
```

나중에 자료가 바뀔 때마다:
```
작업자료 폴더에서 바뀐 것들을 GitHub에 다시 백업해 줘.
메모는 오늘 날짜로.
```

**결과 형태:**
- 폴더 내용이 GitHub에 안전하게 복사됩니다.
- 컴퓨터가 고장 나거나 파일을 실수로 지워도, GitHub에서 다시 내려받을 수 있습니다.

**주의점:**
- GitHub은 코드·문서처럼 가벼운 파일에 맞습니다. 개당 100MB가 넘는 큰 파일(고화질 영상, 대용량 원본)은 올라가지 않거나 막힙니다. 그런 자료는 구글 드라이브 같은 곳이 낫습니다. 에이전트에게 "큰 파일은 빼 줘"라고 미리 말하면 알아서 제외합니다.
- 백업은 "가끔"이 아니라 "정기적"이어야 의미가 있습니다. 7편(자동화)과 연결하면 매일 자동 백업도 가능합니다.

## 시나리오 C — 팀 협업 (여러 명이 같은 문서를 잃지 않고 편집)

여러 사람이 하나의 문서를 고칠 때, 카톡으로 "최종_진짜최종_v3.docx"를 주고받는 혼란을 없앱니다.

**실제 지시문 예시:**
```
우리 팀 공용 문서를 GitHub에서 같이 관리하려고 해.
- "team-handbook"이라는 저장소를 만들고 지금 문서를 올려 줘.
- 팀원 세 명(깃허브 아이디: aaa, bbb, ccc)을 이 저장소에 초대해서
  같이 편집할 수 있게 권한을 줘.
```

팀원이 각자 고친 뒤 합칠 때:
```
팀원들이 올린 수정 내용을 지금 내 폴더로 받아 와서 합쳐 줘.
겹치는 부분이 있으면 어디가 충돌인지 알려 줘.
```

**결과 형태:**
- 팀원 모두가 같은 창고에서 문서를 편집하고, 누가 무엇을 바꿨는지 이름과 함께 기록됩니다.
- 두 사람이 같은 줄을 동시에 고치면 "충돌"로 표시되어, 덮어쓰기로 한쪽 작업이 사라지는 사고를 막아 줍니다.

**주의점:**
- 팀 협업은 가장 강력한 기능이지만, 여러 명이 동시에 고칠 때 "합치기(병합)" 개념을 조금은 이해해야 매끄럽습니다. 처음에는 "한 번에 한 명씩 고치고 올리기" 규칙으로 단순하게 시작하는 것을 권합니다.
- 문서는 텍스트 형식(.md)일 때 협업이 가장 깔끔합니다. 워드 파일은 "동시 편집 후 합치기"가 어렵습니다.

## 시나리오 D — GitHub Pages로 무료 홈페이지·포트폴리오 배포

5편에서 만든 웹페이지를, 실제 인터넷 주소가 있는 홈페이지로 무료 공개하는 방법입니다. **GitHub Pages**는 GitHub이 제공하는 무료 홈페이지 호스팅 서비스입니다. HTML·CSS·자바스크립트 파일을 저장소에 올리면 그대로 웹사이트로 띄워 줍니다.

**실제 지시문 예시:**
```
5편에서 만든 포트폴리오 페이지(index.html)를 인터넷에 무료로 공개하고 싶어.
- GitHub에 공개 저장소를 만들고 이 파일들을 올려 줘.
- GitHub Pages 기능을 켜서 실제 주소로 접속되게 설정해 줘.
- 다 되면 내가 접속할 수 있는 주소를 알려 줘.
```

**결과 형태:**
- 저장소가 만들어지고, GitHub Pages가 켜집니다.
- `https://내아이디.github.io/저장소이름` 형태의 실제 주소가 나옵니다. 이 주소를 누구에게나 공유할 수 있습니다.
- 개인·조직 이름으로 만든 `내아이디.github.io` 저장소는 계정당 하나의 대표 사이트가 되고, 주소가 `https://내아이디.github.io`로 더 깔끔해집니다.

**주의점:**
- GitHub Pages는 **정적 사이트**만 됩니다. 즉 미리 만들어 둔 화면(소개·포트폴리오·안내 페이지)을 보여주는 것까지입니다. 방문자가 로그인하거나 결제하는 "작동하는 기능"은 안 됩니다(5편의 경계와 같습니다).
- GitHub Pages로 무료 공개하려면 저장소가 **공개(public)** 여야 합니다(무료 요금제 기준). 그러니 남에게 보여도 되는 내용만 올리세요. 개인정보·비공개 자료는 넣지 마세요.
- 파일을 고쳐 다시 올리면 잠시 뒤(보통 1~2분) 홈페이지에도 자동 반영됩니다.
- 내 도메인(예: myname.com)을 따로 사면 그 주소로 연결할 수도 있지만, 처음에는 기본 주소로 충분합니다.

## 시나리오 E — 이슈(issue)로 할 일 관리

**이슈**는 원래 개발자가 버그를 기록하는 기능이지만, 비개발자에게는 그냥 **"이 프로젝트에 붙는 할 일·메모 게시판"** 입니다. 문서나 홈페이지 저장소 안에서 "여기 고쳐야 함", "이 내용 추가하기" 같은 할 일을 목록으로 관리할 수 있습니다.

**실제 지시문 예시:**
```
포트폴리오 저장소에 할 일 몇 개를 이슈로 등록해 줘.
1) "프로필 사진 교체하기" — 급함 표시
2) "작업 사례 2개 더 추가"
3) "연락처 이메일 오타 수정"
각각 짧은 설명도 붙여 줘.
```

**결과 형태:**
- GitHub 저장소의 "Issues" 탭에 할 일 3개가 목록으로 등록됩니다.
- 각 항목은 완료하면 체크해 닫을 수 있고, 급함 같은 라벨(꼬리표)을 붙여 분류됩니다.
- 팀원과 함께라면 "이 할 일은 누구 담당"이라고 지정할 수도 있습니다.

**주의점:**
- 혼자 쓰는 간단한 할 일은 메모 앱이 더 편할 수 있습니다. 이슈의 진가는 "그 문서·홈페이지와 할 일이 같은 곳에 붙어 있어서 맥락이 안 흩어질 때" 나옵니다.

## 정리 — 개발 안 해도 이만큼 쓴다

| 용도 | GitHub이 해 주는 것 | 무료로 되나 |
|---|---|---|
| 글·문서 버전 관리 | 언제 뭘 왜 바꿨는지 전부 기록, 되돌리기 | 됨(비공개도 무료) |
| 자료 백업 | 컴퓨터 고장에도 안전한 인터넷 복사본 | 됨(큰 파일 제외) |
| 팀 협업 | 여러 명이 문서를 잃지 않고 편집·합치기 | 됨 |
| 무료 홈페이지(Pages) | 실제 주소가 있는 소개·포트폴리오 사이트 | 됨(공개 저장소) |
| 할 일 관리(이슈) | 프로젝트에 붙는 할 일 게시판 | 됨 |

핵심은 이것입니다. **GitHub은 "코드 창고"가 아니라 "기록이 남는 협업 창고"** 입니다. 그리고 터미널 에이전트 덕분에, 그 창고를 명령어 없이 말로 부려 쓸 수 있게 됐습니다.

## 팩트 체크 메모 (2026-08-29 기준)
- GitHub Pages: 저장소의 HTML·CSS·JS를 그대로 받아 웹사이트로 배포하는 **정적 사이트 호스팅** 서비스. 공식 문서 확인(docs.github.com).
- 무료 요금제: 공개 저장소에서 GitHub Pages 사용 가능. 비공개 저장소 Pages는 유료 플랜(Pro/Team 등) 필요 — 그래서 "무료 공개는 public 저장소"로 안내.
- 사이트 주소: 사용자/조직 사이트는 `<owner>.github.io`(계정당 1개), 프로젝트 사이트는 `<owner>.github.io/<저장소명>`. 공식 문서 표 확인.
- 방문자 IP는 보안 목적으로 기록됨(공식 문서 명시) — 민감 내용 비공개 경고와 일관.
- 큰 파일 한계: GitHub은 개당 100MB 초과 파일에 부적합(대용량은 별도 저장소 서비스 권장) — 표준 사실.
- 터미널 에이전트의 git/GitHub 연동(저장소 생성, 커밋, 푸시, gh CLI 활용)은 Claude Code/Codex의 검증된 표준 기능. 비개발자가 자연어로 위임 가능한 부분만 예시화.
- 개념 근거: [[agent-workflow-developer]]의 버전관리·배포 파이프라인을 비개발자 눈높이로 환원.
