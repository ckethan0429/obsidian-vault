# 에이전트 위임을 위한 업무 프로세스 거버넌스

에이전트에게 결과만 요구하는 것이 아니라, 먼저 **일하는 방식을 검증 가능한 프로세스로 정의하고 그 프로세스의 실행을 위임**한다. 핵심은 행위자가 사람인지 에이전트인지가 아니라, 각 단계에 입력·도구·산출물·검증·승인·복구 규칙이 존재하는지다. 장기 실행과 권한 관점은 [[agent-process-lifecycle]], 실행 인프라는 [[agent-runtime-vertical-integration]]과 연결된다.

## 핵심 명제

> 에이전트에게 결과를 맡기는 것이 아니라, 검증 가능하고 되돌릴 수 있는 업무 프로세스를 맡긴다.

업무는 대화가 아니라 상태 전이로 본다.

~~~text
입력 → 계획 → 계획 검토 → 실행 → 자동 검증 → 독립 리뷰
    → 승인 → 배포/적용 → 관찰 → 학습
~~~

각 상태는 통과 증거가 있어야 다음 상태로 넘어간다. 승인 주체는 사람이거나 정책 기반 에이전트일 수 있다.

## 업무 단위 계약

| 항목 | 정의할 내용 |
|---|---|
| 입력 | 요구사항, 선행 조건, 참조 자료 |
| 행위자 | 사람, 에이전트, 자동화 시스템 |
| 도구 | 검색, 코드 도구, 브라우저, 테스트, 배포 도구, 스킬 |
| 산출물 | 코드, 문서, 테스트 결과, 배포 결과 |
| 완료 조건 | Acceptance Criteria, 품질 기준, 정책 |
| 증거 | 로그, diff, 테스트 리포트, 스크린샷, 커밋 SHA |
| 검토자 | 실행자와 독립된 사람 또는 모델 |
| 승인자 | 다음 단계 진입을 결정하는 주체 |
| 실패 처리 | 재시도, 수정, 중단, 롤백, 에스컬레이션 |

이 계약이 없으면 에이전트는 작업을 시작하기보다 먼저 누락된 조건을 채워야 한다.

## Maker, Checker, Approver 분리

- **Maker**: 계획·코드·문서 등 산출물을 만든다.
- **Checker**: 요구사항 충족, 오류, 회귀, 보안, 운영 가능성을 독립적으로 검토한다.
- **Approver**: 증거와 위험도를 종합해 진행·수정·중단을 결정한다.

같은 주체가 Maker와 Checker를 모두 맡으면 자기 확증과 공유된 오류가 생긴다. 최소한 검토 컨텍스트를 새로 구성하고, 중요한 작업은 다른 사람이나 다른 모델 계열을 사용한다.

모든 단계에 사람의 수동 승인이 필요하다는 뜻은 아니다. **모든 상태 전이에 검토 또는 승인 게이트가 필요하다**는 뜻이다.

## 멀티모델 검토 구조

| 역할 | 주 시야 |
|---|---|
| Planner | 요구사항 분해, 영향 범위, 위험, 순서 |
| Executor | 실제 구현과 도구 실행 |
| Reviewer | 논리, 누락, 유지보수성, 요구사항 충족 |
| Test Agent | 경계 조건, 회귀, 실패 재현 |
| Security Agent | 권한, 비밀정보, 공급망, 파괴적 행위 |
| Approver | 증거 종합과 위험 인수 |

모델 수보다 중요한 것은 **실패 양상의 독립성**이다. 같은 기반 모델을 여러 번 호출하는 것은 상관된 실패를 만들 수 있다. 역할별로 프롬프트, 컨텍스트, 도구 권한, 모델 계열을 분리하고 결과가 충돌하면 상위 검토로 올린다.

## 위험 기반 승인 정책

| 위험도 | 예시 | 권장 게이트 |
|---|---|---|
| 낮음 | 읽기, 검색, 초안 | 자동 검증 또는 Reviewer 승인 |
| 보통 | 문서 수정, 비파괴 설정 변경 | 독립 Reviewer + 실행 증거 |
| 높음 | 코드 병합, 외부 전송, 스테이징 배포 | 다중 검토 또는 사람 승인 |
| 치명적 | 프로덕션, 결제, 데이터 삭제, 권한 확대 | 사람의 명시적 승인 + 롤백 준비 |

가역성, 영향 범위, 실패 비용, 신뢰 이력이 승인 강도를 결정한다. 이는 [[agent-process-lifecycle]]의 신뢰 사다리와 연결된다.

## 개발자 업무 프로세스 예시

### 0. 업무 접수
- 이슈, 요구사항, 완료 조건, 영향 환경을 확인한다.
- 산출물: 작업 정의, Acceptance Criteria, 테스트·롤백 계획.
- 게이트: 요구사항이 모호하면 구현을 시작하지 않는다.

### 1. 코드베이스 온보딩
- 온보딩 문서, 프로젝트 구조, 실행·테스트 명령, 브랜치 전략, CI/CD를 읽는다.
- 산출물: 관련 디렉터리, 데이터 흐름, 배포 경로 요약.
- 게이트: 문서 설명과 실제 코드·파이프라인이 일치하는지 확인한다.

### 2. 태스크 분석과 브랜치 생성
- 작업을 작은 단위로 나누고 의존성, 위험, 변경 예상 파일을 정리한다.
- 작업 서브브랜치를 생성한다.
- 게이트: 구현 전 계획 리뷰를 통과한다.

### 3. 관련 코드 탐색
- 호출 관계, 기존 패턴, 유사 기능, 테스트, Git 이력을 찾는다.
- 산출물: 변경 대상과 회귀 가능 영역.
- 게이트: 기존 기능 재사용 가능성과 변경 범위를 검토한다.

### 4. 단계별 구현과 커밋
- 데이터 모델, 비즈니스 로직, UI, 테스트, 문서를 되돌릴 수 있는 단위로 나눈다.
- 각 커밋은 빌드 가능하고 목적이 하나여야 한다.
- 게이트: 정적 분석과 최소 테스트를 통과한 커밋만 체크포인트로 인정한다.

### 5. 로컬 검증
- 타입 검사, Lint, 단위·통합·E2E 테스트, 빌드, 직접 기능 확인을 수행한다.
- 산출물: 명령, 결과, 실패 로그, 화면 증거.
- 게이트: “테스트했다”는 진술이 아니라 실행 증거를 검토한다.

### 6. 원격 저장소 푸시와 PR
- 원격 브랜치에 푸시하고 변경 목적, 테스트 결과, 영향 범위, 롤백 방법을 PR에 기록한다.
- 게이트: 비밀정보, 불필요한 파일, 예상 밖 diff가 없는지 확인한다.

### 7. CI
- 빌드, 타입, Lint, 테스트, 보안·의존성 검사, 산출물 생성을 자동 실행한다.
- 게이트: 필수 Job과 품질 기준을 통과해야 한다. 테스트 우회는 별도 승인이 필요하다.

### 8. 독립 리뷰
- 요구사항, 설계, 예외 처리, 회귀, 보안, 운영성, 테스트 실효성을 검토한다.
- 가능하면 구현자와 다른 모델 또는 사람이 맡는다.
- 게이트: 지적 사항 해소와 재검증이 끝나야 병합한다.

### 9. 스테이징 병합과 CD
- 스테이징에 병합하고 배포 파이프라인 실행, 커밋 SHA, DB 마이그레이션, 기동 상태를 확인한다.
- Smoke Test와 로그·오류율을 확인한다.
- 게이트: “파이프라인 성공”과 “정상 배포”를 별도로 증명한다.

### 10. 프로덕션 승인과 배포
- 스테이징 증거와 위험도를 종합해 main 반영과 프로덕션 배포를 승인한다.
- 게이트: 고위험 변경은 사람의 명시적 승인과 롤백 준비가 필요하다.

### 11. 배포 후 관찰
- 오류율, 응답 시간, 자원, 핵심 사용자 흐름, 알림을 이전 버전과 비교한다.
- 사전 정의한 임계치를 넘으면 자동 또는 수동 롤백한다.

### 12. 학습과 프로세스 개선
- 실패를 테스트 케이스로, 반복 작업을 스킬로, 판단 기준을 정책으로 변환한다.
- 로그를 새 모델·하네스의 평가 세트로 재사용한다. [[managed-agents-architecture]]의 append-only 세션 로그는 이 단계의 근거가 된다.

## 증거 중심 운영

단계 완료는 에이전트의 주장으로 판정하지 않는다. 다음 증거를 가능한 한 기계적으로 수집한다.

- 요구사항과 구현의 추적 관계
- 변경 diff와 커밋 SHA
- 테스트 명령, 결과, 커버리지
- CI/CD Job 상태와 배포 버전
- 운영 지표와 Smoke Test
- 승인 주체, 시각, 근거
- 실패, 재시도, 롤백 이력

이를 통해 결과를 재현하고, 사고 시 어느 게이트가 실패했는지 추적할 수 있다.

## 마케터로의 확장

같은 골격의 마케터 적용은 [[agent-workflow-marketer]]에 둔다. 개발자의 CI가 빌드와 테스트라면, 마케터의 CI는 클레임·트래킹·예산·채널 스펙이다. CD는 채널 게시와 지출이고, 롤백은 광고 중지와 정정이다.

## 일반화

이 구조는 개발 외 업무에도 동일하게 적용된다.

- 위키: 자료 수집 → 출처 검증 → 초안 → 독립 검토 → 게시 → 링크·로그 확인
- 마케팅: 브리프 → 자산 검증 → 초안 → 독립 검토 → 소프트 런치 → 본 집행·관찰 ([[agent-workflow-marketer]])
- 영업: 리드 수집 → 자격 검증 → 제안 → 법무·가격 승인 → 전송 → 후속 관찰
- 인프라: 변경 계획 → 영향 분석 → 백업 → 스테이징 → 승인 → 적용 → 모니터링·롤백

도메인마다 도구는 달라져도, 상태·증거·게이트·복구라는 골격은 같다.
