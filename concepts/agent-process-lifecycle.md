# 에이전트 프로세스와 라이프사이클 (엔드유저 용도 3분류 기준)

"완성된 에이전트는 어떤 프로세스가 될까"를 엔드포인트 유저의 실제 사용 패턴에서
출발해 정리한다. 인프라 층 구분은 [[agent-runtime-vertical-integration]] 참조.

## 출발점: 엔드유저 용도 3분류 (CK 실사용 기준)

| | 1. 일상 질문형 | 2. 업무 자동화형 | 3. 코딩 에이전트형 |
|---|---|---|---|
| 예시 | 검색 대체, ChatGPT 용도 | 서치, 위키 자료 정리, 크론잡 | 개발, CI/CD, 테스트 |
| 실행 형태 | **함수** (호출→응답→소멸) | **프로세스** (상시 구동/스케줄) | **프로젝트** (장시간 세션) |
| 호출 패턴 | 사람이 먼저 (pull) | 이벤트/스케줄이 먼저 (push) | 태스크 단위 위임 |
| 수명 | 초 단위 | 무기한 (수면↔기상 반복) | 시간~일 단위 |
| 필요한 층 | 프론티어 모델 단발 | durable runtime + 루틴 + 메모리 | 샌드박스 + 세션 로그 + 검증 |
| 실패 비용 | 낮음 (재질문하면 됨) | 중간 (조용히 틀린 게 쌓임) | 높음 (배포·데이터 파괴 가능) |
| 신뢰 요구 | 거의 불필요 | 핵심 (무감독 반복 실행) | 핵심 (권한 큰 행동) |
| 검증 방식 | 사람이 즉석 판단 | 샘플링 검사 | E2E 테스트가 일급 단계 |

- 용도별로 요구하는 스택 깊이가 다르다: 1번은 모델 게이트웨이만 있으면 되고,
  2번부터 durable runtime이 필수가 되며, 3번에서 샌드박스·검증이 비대해진다
- 실패 비용의 비대칭이 세그먼트를 가른다. 같은 모델이라도 1번에선 오답이 싸고
  2·3번에선 비싸므로, 신뢰·검증 인프라 투자가 용도에 비례해야 한다
- 주의: 2번의 실패는 시끄럽지 않다. 크론잡이 조용히 틀린 결과를 쌓는 것이
  가장 늦게 발견되는 실패 모드

## 런타임 프로세스 루프: 완성형 에이전트의 "하루"

```
[수면] → (이벤트/스케줄 트리거) → [지각] → [트리아지: 깨어날 가치 판단(싼 모델)]
  → [계획(프론티어)] → [실행: isolate 기본, 필요시 샌드박스/브라우저]
  → [검증: E2E로 자기 결과 확인] → [에스컬레이션: 판단 필요 지점만 인간에게]
  → [납품: 실제 도구에 랜딩] → [정리: 로그→메모리·루틴·스킬 추출] → [수면]
```

- 핵심 전환은 **함수에서 프로세스로**: running / waiting / sleeping 상태를 가진
  존재. 대부분의 시간은 sleeping이고 durable runtime 덕에 그 비용은 0에 수렴
- 트리아지는 오픈웨이트, 계획·판단은 프론티어 — 모델 게이트웨이 라우팅 5축이
  루프 단계에 그대로 매핑됨
- 정리(consolidation) 단계가 학습: 세션 로그에서 반복 패턴→루틴, 교정→선호 추출
- 용도별 루프 사용 범위: 1번은 계획→납품 구간만 쓰는 퇴화형, 2번은 전체 루프,
  3번은 실행·검증 구간이 비대해진 형태

## 라이프사이클: 디지털 워커 고용 주기 (ADLC)

1. **온보딩** — identity 발급(계정·크리덴셜·권한), 도구 접속, 팀 컨텍스트 주입
2. **수습** — 낮은 권한 + 높은 승인 빈도, 시연 학습(한 번 보여주면 루틴화)
3. **신뢰 사다리** — 성공 이력에 비례해 무승인 실행 범위 확대
4. **성과 관리** — 세션 로그가 곧 근태·성과 기록, 회귀 감지·재교육
5. **조직화** — 레인별 전문 에이전트 + chief-of-staff, 에이전트 간 위임
6. **오프보딩** — 권한 회수, 메모리·루틴을 후임으로 이관

용도 3분류와의 관계: 1번은 라이프사이클이 거의 없고(무상태), 2번은 2~4단계가
가치의 대부분이며, 3번은 1단계(레포 권한·CI 크리덴셜)와 4단계(회귀)가 무겁다.

## 운영 컨트롤 플레인의 3축

### OS 축 — 자원 효율
- 질문: "이 프로세스에 자원을 줄 가치가 있나"
- 결정: 언제 깨울까, 어디서 돌릴까(isolate/컨테이너/브라우저), 언제 재울까
- 지표: 활용률, 레이턴시, 작업당 비용. 대응물: K8s 스케줄러, Proxmox 오버커밋,
  @cloudflare/computer

### HR 축 — 신뢰·품질
- 질문: "이 워커에게 권한을 줄 가치가 있나"
- 두 핵심 지표: **성실도**(완결률·검증 통과율·재작업률 — 90% done과 100% done의
  차이)와 **빈도수**(에스컬레이션 빈도, 체크인 필요 주기)
- 대응물: Grok Bot의 trust-over-time, 승인 모드(read-only/guard/full-access)

### 퀀트 축 — 확률적 판단
- 신뢰는 점수가 아니라 **분포**: 10건의 98%와 1,000건의 98%는 다른 신뢰.
  베이지안 업데이트로 사후분포 갱신, 신규 에이전트 cold start는 prior 이전으로
- 위임 결정은 **기대값 계산**: EV(자율) = P(성공)×가치 − P(실패)×실패비용 −
  컴퓨트비용 vs EV(에스컬레이션). 실패비용 비대칭(가역/비가역)이 결정을 지배
- 권한 크기 = **포지션 사이징** (Kelly적 사고: 승률·손익비에 비례)
- 수습은 **bandit 문제**: 저위험 작업을 신규 에이전트에 흘려 분포를 좁히는
  탐색(exploration) 비용을 의도적으로 지불
- 에이전트 팀은 **포트폴리오**: 같은 모델 기반은 실패 모드를 공유(상관 리스크).
  오픈웨이트+프론티어 혼합은 비용 절감이자 분산 효과. 리스크 버짓 배분 가능
- **세션 로그 = 백테스트 데이터**: append-only 이벤트 로그에 새 하네스/모델
  버전을 리플레이해 배포 전 검증 ([[managed-agents-architecture]]의 session 분리가
  이걸 가능하게 하는 구조)
- 검증도 확률적으로: 신뢰 비례 샘플링 검사 (acceptance sampling), 연속 실패 시
  자동 권한 강등 (circuit breaker / stop-loss)

### 3축의 피드백 루프
- 승인 대기 = CPU idle, 에스컬레이션 = 인터럽트: HR 지표가 나쁘면 자원 효율도
  나빠진다
- 따라서 **신뢰가 곧 스케줄링 파라미터**: 성실도 높고 빈도수 낮은 에이전트에
  더 긴 타임슬라이스·큰 배치·무감독 야간 실행을 자동 허용
- 시장 공백: OS 축은 Cloudflare가 상품화 중, HR 축은 각 제품 안의 암묵 기능.
  셋을 연결한 컨트롤 플레인("완결률 98%·주1회 에스컬레이션 → 야간 무감독 +
  GPU 우선순위 상향"을 자동 결정)은 아직 없다

## 핵심 지표: 인간 판단 1회당 완결되는 일의 양

- 루프가 완성될수록 인간의 역할은 판단점 승인·취향 전달·책임으로 수렴
- 시스템 설계 목표는 "에이전트가 얼마나 잘하나"가 아니라 **인간 판단 1회당
  완결량**. 에스컬레이션이 정확한(불필요한 질문 없는) 에이전트가 이긴다 —
  smooth AI infra experience 원칙의 종착점

## CK 시사점

- 용도 3분류는 그대로 상품 세그먼트: 1번은 커모디티(모델 게이트웨이 경쟁),
  2번이 durable runtime·신뢰 인프라의 주 수요처, 3번이 샌드박스·검증의 주 수요처
- VirtOn 로드맵 관점: 컴퓨트 층([[agent-runtime-vertical-integration]]) → 매니지드
  인퍼런스([[GPU_브로커리지_PLG_전략_단계별_설계_2026-03-05]]) 다음 카테고리로
  "에이전트 인사 시스템"(신뢰 사다리·권한·성과 로그 컨트롤 플레인)이 온다
- CK 도메인 3개(AI 에이전트, 퀀트, 인프라)가 한 지점에서 만나는 크로스도메인
  신세시스: 퀀트 축의 리스크 관리 프레임이 에이전트 운영의 미개척 부분
