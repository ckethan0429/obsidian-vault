## 1. Background

『다크호스』의 핵심 개념인 **미시적 동기(micro-motives)** 를 기준으로 나의 동기 구조를 정의한다. 미시적 동기는 "성공하고 싶다" 같은 거시적 목표가 아니라, **행위 자체가 재미있어서 시간 가는 줄 모르는 아주 작은 단위의 욕구**다.

Virton 퇴사 결정 이후 "무슨 분야를 해야 하는가"라는 질문을 반복하고 있었고, 산업이 아니라 **내가 반복적으로 끌리는 문제의 형태**를 먼저 정의할 필요가 있었다. 역할·자산 맥락은 [[virton-career-and-business-profile]]에 있다.

## 2. Goals / Non-Goals

**Goals**
- 나의 미시적 동기를 검증 가능한 형태로 문서화한다.
- 이 동기를 창업 방향, 역할 선택, 팀 구성의 판단 기준으로 사용한다.
- 향후 방향 전환 유혹이 올 때 참조할 "제약 조건"을 명시한다.

**Non-Goals**
- 특정 산업(AI 인프라 등)을 최종 확정하는 것
- 성격 유형 분류 (MBTI 등)와의 통합
- 자기 분석을 더 정교화하는 것 (§7 참고)

## 3. Method

1. Claude가 대화 기록 기반으로 후보 동기 5개 제시
2. GPT가 별도 대화 기록 기반으로 후보 제시 → 두 분석을 교차 비교
3. GPT가 제안한 **판단 게임**: 결과(돈·인정·성공)를 배제하고 "행위 자체의 재미" 기준으로 5개 상황의 순위를 매김
4. CK가 실제 순위를 확정 → 두 AI가 재해석

### 판단 게임 항목

| ID | 상황 |
|---|---|
| A | 새 시스템 내부 구조를 며칠 파고들어 원리를 이해했을 때 |
| B | 복잡한 시스템을 직접 설계해 "이렇게 하면 훨씬 깔끔한데?"라는 구조를 만들었을 때 |
| C | 내가 만든 시스템이 실제로 돌아가고 남들이 쓰는 것을 봤을 때 |
| D | 복잡한 문제를 변수와 규칙으로 정리해 "이제 판단할 수 있다"가 됐을 때 |
| E | 내가 아는 것을 설명해 상대가 "아, 이해했다"고 했을 때 |

## 4. Findings

### 4.1 확정 순위: **B → D → C → E → A**

| 순위 | 항목 | 해석 |
|---|---|---|
| 1 | B 설계 | 핵심 동기. 이해가 아니라 **재설계**가 목적 |
| 2 | D 규칙화 | 기술 외 영역(투자, 지분 협상, 사주, AI Agent)에서도 반복. 불확실성을 변수와 규칙으로 바꿈 |
| 3 | C 실제 작동 | 이론적 구조보다 돌아가는 구조. **B-D 루프의 브레이크** 역할 |
| 4 | E 설명 | 동기라기보다 확산 수단. 컨설팅/교육 단독은 부적합 |
| 5 | A 탐구 | 능력은 있으나 목적이 아님. 설계를 위한 **재료/통행료** |

지분 협상 스코어카드의 맥락은 [[virton-equity-negotiation-baseline]]에 있다.

### 4.2 예측 대비

| 분석자 | 예측 | 적중 |
|---|---|---|
| Claude | B A D C E | B 1위만 적중. A를 2위로 본 것은 대화에 디버깅 얘기가 많았던 것을 동기로 오독 |
| GPT (초기) | "이해 → 재설계" 단일 문장 | 방향은 맞았으나 A 비중 과대평가 |

### 4.3 미시적 동기 정의 (합의)

> **복잡하고 불확실한 현실을 내가 설계할 수 있는 구조와 규칙으로 바꾸고, 그 구조가 실제로 작동하는 것을 확인하는 것.**

핵심 동사는 "이해하다"가 아니라 **"설계하다"**.

### 4.4 "통제감"의 재정의

초기 가설: 레버를 쥐는 권한에 대한 욕구.
수정: **내가 설계한 인과관계가 현실에서 그대로 작동하는 감각**. 사람이나 조직에 대한 통제가 아니라 설계의 적중에 대한 욕구. 지분 협상 스코어카드도 대표 통제가 아니라 판단의 구조화가 목적이었음.

### 4.5 자연스러운 Operating Loop

```
복잡한 문제 등장
  → "어떻게 구조화하지?" (B)
  → 규칙 / 추상화 (D)
  → 자동화 → 실제 작동 (C)
  → 제품화 → 전달 (E)
  → 막히면 필요한 만큼만 파고듦 (A)
```

커리어 이동(백업/DR → 가상화 → 프라이빗 클라우드 → AI 인프라 → Agent/Harness)이 산만해 보이지만, "새로운 복잡성이 등장하면 설계 가능한 형태로 만들고 싶다"는 하나의 축으로 설명됨. **기술은 목적이 아니라 재료.** 기술 스택 쪽은 [[ck-technology-engineering-profile]]에 있다.

### 4.6 외부 참조: 억만장자 공통점과의 대조 *(1.0-final 추가)*

영상이 제시한 부자들의 공통점 3가지 — ① 제작자 마인드 ② 선택과 집중 ③ 미시적 동기 — 를 BDCEA에 대조한 결과.

| 영상의 관찰 | 재해석 | 이 스펙에 미치는 영향 |
|---|---|---|
| 젠슨 황은 시계를 안 차고, 머스크는 소유를 최소화 | 절약이 아니라 **주의력 예산**. 미시적 동기 밖의 것에는 돈이 아니라 관심을 안 씀 | R-2 보강: 낭비의 단위는 돈이 아니라 *wedge 밖에서 B를 발동하는 것* |
| 세 가지 공통점은 별개가 아님 | 제작자 마인드 = 선택과 집중 = 미시적 동기의 안팎. 하나의 것 | §4.3 정의 하나로 세 가지가 설명됨 |
| 저커버그는 제품보다 규칙을, 발머는 팀보다 경기장을 만듦 | "제작자"는 물건 제작자가 아니라 **판 짜는 사람**. 레버리지는 B(설계)보다 **D(규칙화)** 에서 나옴 | §8 Open Question — D의 상업적 가치 재평가 |
| 앨리슨의 하와이 섬, 저커버그의 소 목장 | 취미가 아니라 **꺼지지 않는 동기**. 돈이 무한해져도 B→C 루프를 섬 단위, 목장 단위로 계속 돌림 | §8 Open Question — 의무 없는 시간의 행동 관찰이 판단 게임보다 정확한 검증 |
| "부자처럼 살자" | 인과가 반대. 이들은 동기에 맞는 일을 했고 그 동기가 **우연히 규모가 나가는 종류**였을 뿐. 같은 동기라도 C가 없으면 만족한 아키텍트로 끝남 | D-3, D-4: 목표는 부가 아니라 *내 루프가 돌면서 동시에 남이 돈을 내는 교집합* |
| "건강한 몸, 평온한 마음, 사랑하는 가정" | 다크호스의 원래 논지 — 충족은 부의 결과가 아니라 fit의 결과 | Non-Goal 유지: 이 스펙은 부의 최적화 문서가 아님 |

가장 큰 수정 압력은 세 번째 줄. 지금까지 자신을 **설계자(B)** 로 정의했으나, 팔리는 것은 설계가 아니라 **남이 따르는 규칙(D)** 일 가능성. 단, 이는 결정이 아니라 Open Question으로만 둔다 (R-4).

### 5.1 Principles (위키 전역 원칙) *(1.0-final 추가)*

> **Interest is not Evidence. Usage is Evidence.**

관심, 아이디어, 구조, 아키텍처, 시장조사는 모두 B/D 활동이며 증거가 아니다. **실제 사용과 지불**만이 C의 증거다.

| C의 증거 | C의 증거가 아님 |
|---|---|
| 돈을 낸다 | "좋은데요" |
| PoC를 요청한다 | 관심 표명, 명함 교환 |
| 실제 서버를 들고 와 설치를 요구한다 | 설계 문서에 대한 호평 |
| 반복 사용한다 | 데모 시청 |

### 5.2 구조 요약 *(1.0-final 추가)*

```
MICRO-MOTIVE (B → D → C)
        ↓
  SYSTEMS BUILDER
        ↓
Asset-Constrained Wedge (D-3, D-4)
        ↓
Private Cloud / GPU / AIOps / Agent
        ↓
Design → Ship → Use → Learn (D-5)
```

## 6. Risks / Anti-Patterns

| ID | 리스크 | 징후 | 대응 |
|---|---|---|---|
| R-1 | **B-D 함정**: 설계 → 더 좋은 설계 → 추상화 → 프레임워크 → "조금만 더 다듬고…" → 고객 없음 | [[hermes-workspace]], 리드젠 방법론, 스코어카드처럼 구조 만들기 자체가 목적화 | 설계 시작 전 "실제로 돌아가는 날짜"를 먼저 박음 |
| R-2 | **정의 과잉 일반화**: "새로운 복잡성 길들이기"는 로봇·블록체인·보안 어디든 정당화 가능 → 아이디어 생성이 많은 성향에 방향 전환 면허증이 됨 | 6개월 내 다른 "복잡한 것"에 끌림 | 분야는 동기가 아니라 자산(D-4)으로 제약 |
| R-3 | **A 회피**: 설계가 막히면 파고드는 대신 구조를 바꿔 우회 | Ceph, vGPU 등 이해 필수 레이어에서 지연 | D-6 팀 구조 |
| R-4 | **메타 루프**: 자기 분석 자체가 B-D 행위라 즐거움 → 분석 정교화가 C로 이어지지 않음 | 이 문서를 v2, v3로 계속 개정 | 본 문서는 v1.0에서 동결 (§7) |

## 8. Open Questions

- E(설명)가 진짜 동기인지, 창업 준비용으로 억지로 하는 행위인지 미확정 — 블로그/컨설팅을 결과 무관하게 계속하는지로 판단
- C 3위가 실제 사업 국면에서 B-D 브레이크로 충분히 강한지 — 브레이크는 B-D를 중단하라는 뜻이 아니라, 설계→더 나은 설계→프레임워크로 무한히 도는 루프(R-1)를 **어느 시점에 끊고 실제로 내보내는 힘**을 뜻함. AC-3에서 확인: 5명의 답을 들은 뒤 그 답으로 범위를 확정하고 만들기 시작하면 Pass, 답을 듣고도 "피드백 반영한 더 나은 아키텍처"로 다시 B-D로 돌아가면 Fail. C 이후에는 B-D가 고객 피드백을 입력으로 받아 다시 돌아야 정상
- "구조가 깨지는 순간에 끌린다"(GPT)가 안정기 진입 후 이탈 욕구로 작용하는지 — Virton 퇴사 동기와 분리 필요
- *(1.0-final 추가)* D(규칙화)가 개인적 재미를 넘어 상업적 레버리지인지 — 억만장자 공통점의 "제작자"는 제품 제작자가 아니라 **남이 따르는 규칙(판)을 만드는 사람**. 여기서 판은 플랫폼만이 아니라 "남들이 그 안에서 움직이게 되는 규칙" 전부: 플랫폼(그 위에서 만들게 함), 표준/프로토콜(그 형식에 맞추게 함, 예: K8s API·OpenTelemetry), 레퍼런스 아키텍처/운영 절차("이렇게 하는 게 맞다"고 따르게 함), 가격·계약 구조(그 단위로 생각하게 함, 예: 소켓당 과금), 인증/평가 기준. 제품(B)보다 고객이 따르게 되는 운영 규칙·표준(D)을 먼저 쥐는 전략이 유효한지 AC 결과와 함께 판단. 작은 팀에는 플랫폼보다 표준·레퍼런스 아키텍처 선점이 현실적
- *(1.0-final 추가)* 의무 없는 시간에 손이 무엇을 만드는가 — 판단 게임보다 정확한 검증. 관찰 기록 필요
